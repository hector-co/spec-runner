## Why

SpecRunner's stated purpose is to drive OpenSpec workflows by watching issue
and PR comments, but today it only tests the repository connection and
exits — `IGitService`/`IGitHubService` are `NotImplementedException`
placeholders and nothing reacts to a comment. This change implements the
first end-to-end workflow: a maintainer commenting `/propose` on an open
issue gets a branch, an OpenSpec proposal generated by the CLI coding
agent, and a draft PR, with progress reflected back on the comment via
reactions so re-runs don't reprocess the same comment twice.

## What Changes

- Implement `IGitService` (`SpecRunner.Git`) for real: pull the base
  branch, hard-reset the local clone, create/switch to a branch, stage and
  commit, and push — replacing the current `NotImplementedException`
  placeholder. **BREAKING**: callers relying on the placeholder throwing
  will now see real git side effects.
- Extend and implement `IGitHubService` (`SpecRunner.GitHub`) for real:
  list open issues with their comments, read/add reactions on a comment,
  create an issue comment, and create a draft pull request — replacing the
  current `NotImplementedException` placeholder and adding the members the
  workflow needs beyond what was originally scoped (read/write PR
  comments, mark ready for review remain interface-only until a future
  `/update`-handling change needs them).
- Add a new `propose-workflow` capability: a single scan pass, run once per
  `SpecRunner.Console` invocation, that finds open-issue comments whose
  body starts exactly with `/propose` and that the bot hasn't already
  reacted to, marks each as in-progress, resolves the spec name, resets
  the local clone to the base branch, creates a `feature/{issue-number}`
  branch, runs the CLI coding agent with an `/opsx-propose` prompt built
  from the issue description, and on success commits, pushes, and opens a
  draft PR; every outcome (success, already-has-a-PR, error/timeout) is
  reflected back onto the triggering comment via a reaction and a reply,
  and recorded in the state store.
- Modify the `SpecRunner.Console` entry point so that, after a successful
  repository connection test, it runs one `propose-workflow` scan pass
  before exiting, instead of performing no git/GitHub operation.

## Capabilities

### New Capabilities
- `git-operations`: real implementation of pull, hard reset, branch
  create/switch, commit, and push against the configured local clone.
- `github-operations`: real implementation of listing open issues and
  their comments, reading/adding comment reactions, creating an issue
  comment, and creating a draft pull request, plus resolving the
  authenticated bot identity used to recognize its own reactions.
- `propose-workflow`: the orchestration of the `/propose` comment
  lifecycle described above, including its GitHub-reaction status
  protocol and state-store recording.

### Modified Capabilities
- `state-store-schema`: the "Git and GitHub service contracts are defined
  but unimplemented" requirement is replaced — `IGitService` and
  `IGitHubService` are now real implementations (see `git-operations`,
  `github-operations`) rather than placeholders that throw.
- `solution-layout`: the console entry point requirement changes from
  "connection test only, no git/GitHub operation" to "connection test,
  then one `propose-workflow` scan pass" before exiting.

## Impact

- `SpecRunner.Core`: new `IProposeWorkflowRunner` abstraction; extended
  `IGitHubService` surface (issue/comment listing, reactions, issue
  comments, draft PR creation); no new projects.
- `SpecRunner.Git`: real `IGitService` implementation using the local
  clone at `SpecRunnerOptions.LocalRepositoryPath`.
- `SpecRunner.GitHub`: real `IGitHubService` implementation calling the
  GitHub REST API with the configured PAT.
- `SpecRunner.Console`: composes `IGitService`, `IGitHubService`,
  `IStateStore`, `ICliAgentSessionFactory`, and `ISpecNameResolver` into
  the `IProposeWorkflowRunner` implementation; entry point runs one scan
  pass after the connection test.
- `SpecRunner.State`: no schema change expected — existing tracked-issue/
  tracked-comment shape already covers this workflow's needs.
- Out of scope: `/update`, `/implement`, `/archive` comment handling; PR
  review-comment handling; a continuous polling/daemon loop (each console
  invocation performs one scan pass; repeated invocation is left to
  external scheduling); retry/backoff beyond the existing per-task
  timeout.
